## 1. 范围前提（先说清楚，否则"齐全"无从谈起）

需求报告写的是**完整产品**（含登录/速记/统计）；本项目经需求方确认后**裁掉**三块：

| 模块 | 处理 | 连带影响 |
| --- | --- | --- |
| §3.1 登录（本地用户名单、会话保持、示例账号、退出） | 不做 | 报告人改为"本机个人信息配置"；"我的"页不显示部门编码/工号、无退出登录 |
| §3.2 速记（工作台：文字 + 图片） | 不做 | 1.3 核心价值里的"速记"、3.6 统计里的"速记数"随之不做 |
| §3.6 统计（报告量、7 天活动、类型 Top5） | 不做 | — |
| 膜厚检测 / 玻璃检测 | 不做 | 需求报告本身未涉及（属产品线外观需求，另行确认范围外） |

导航也随之从"4 个主 Tab（应用/项目/统计/我的）"收敛为**3 个**：项目 / 报告 / 我的
（原「应用」下的"检测填报 + 报告管理"合并为「报告」，「工作台（速记）」随速记一起裁掉）。

## 3. 与需求文字的 5 处差异（都是有意为之，逐条说明）

| # | 需求原文 | 实际实现 | 为什么 |
| --- | --- | --- | --- |
| 1 | 报告人/部门"取当前登录用户，不可改" | 取"本机个人信息配置"，默认 检测员/检测部，可在「我的 → 个人信息配置」改 | 本期无登录（范围裁剪）；现场每台设备署名不同，但要能改 |
| 2 | 附页信息表 **8 个标签** | **9 行**（多一行「图片文件」） | 客户真实报告的附页有这一行；闸门 B 对齐真实报告时按实文件走 |
| 3 | 横梁预置条文 **2 条** | **3 条**（多一条"两句合并"写法） | 真实报告里该列出现过合并写法，收进来才能与实文件一致 |
| 4 | 检测面"1~6 个（A~F）" | 上限 6 不变，但**标签可选**（立柱建议 B/H、横梁建议 t，也可自由输入） | 真实数据里出现 B / H / t；A~F 只是示例。自由输入不会丢数据 |
| 5 | 导航 4 个 Tab + 应用内 3 个子 Tab | 3 个 Tab（项目 / 报告 / 我的） | 速记裁掉后，"应用"层没有存在必要；检测填报与报告管理合并进「报告」 |

## 4. 复核方式（可重跑）

```powershell
python tools/verify_all.py     # 250 前端 + 348 Python + 16 条版式/对拍闸门（0 差异）
npm run test:e2e               # 21 条真实浏览器 E2E（主流程 + 边界 + 离线 + 图片链路）
npm run test:android           # 安卓真机/模拟器回归（含相机、真实 dialog、备份导入）
```

本次检查额外做的静态核对（代码级）：

- `webapp/config.py`：`DEFECT_TYPES`(10 项)、`REQUIREMENT_OPTIONS`(2/3 条)、`FACE_MAX_COUNT`(6)、
  `THICKNESS_VALUE_COUNT`(5)、`NOTE_TEXT`、`REPORT_FILENAME`、`ATTACHMENT_TITLE`、`ATTACHMENT_ORDER`(9 行)
- `views/reports.js`：8 个字段 + 等级三选一（默认中）+ 自定义类型联动 + 「不绑定」默认项
- `views/records.js`：`+ 添加检测面`（上限 6）+ 每面 5 值 + 编辑时模板锁定（无切换入口）
- `report/engine.js`：章节条件渲染（`if (!group.records?.length) continue`）、备注只推一次、附页 `pageBreakBefore`

## 5. 建议（要不要做，请你定）

1. **§3.4 f（可选）单份报告导出为文本/JSON** —— 需求标可选。纯前端加一个"导出 JSON"按钮约 40 行，
   好处是便于把单条缺陷丢进别的系统；坏处是多一个交付面。**建议不做**，除非客户明确要。
2. **「我的」页补"部门编码"** —— 现在只有姓名/部门。如果客户现场要用部门编码做报告归档标识，
   加上去很便宜（一个字段 + 附页可选显示）。**需要你确认客户是否真用**。
3. **需求文档本身建议回写** —— 把 §3.1/§3.2/§3.6 标为"本期不做"、把 3.3.2 报告人改成
   "取本机配置"、把导航改成 3 个 Tab，这样"需求—实现—验收"三份文档口径一致（Final Report 里也能直接用）。
