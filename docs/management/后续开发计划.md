# 建筑幕墙检测管理 APP —— 后续开发计划

> 编制日期：2026-09-06
> 面向目标：在现有 Flask PoC 基础上，按已确认的 MVP 范围完成可实际使用的检测报告工作流，
> 交付参考节点为 12 月中旬（约 15 周开发节奏）。

## 1. 背景与范围确认

当前已完成一个最小 PoC：缺陷检测填报 → 存入 SQLite → 单条记录导出 Word，仅用于验证链路可行性。

已确认的范围口径：

- **MVP 包含**：项目基本信息、幕墙立柱/横梁两种检测记录模板、项目级 Word 报告导出、缺陷检测填报、报告管理。
- **MVP 不包含**：真实样例 `金骐智谷_金骐_检测报告.docx` 中的“幕墙玻璃尺寸及厚度检测结果”模块。该样例仅作为立柱/横梁表格版式的参照。
- **样例文档实际结构**（已用 python-docx 解析确认）：
  1. 项目基本信息段落（项目编号/房屋名称/房屋地点/委托单位/检测日期，逐行文本）；
  2. “幕墙立柱截面尺寸检测结果”标题 + 表格（楼层、构件位置、尺寸结果、厚度检测 1~5 个读数 + 最小值、立柱截面尺寸要求）；
  3. “幕墙横梁截面尺寸检测结果”标题 + 同结构表格（要求列文案不同）；
  4. “幕墙玻璃尺寸及厚度检测结果”——**MVP 不输出**；
  5. 备注段固定文案：`备注：检测构件位置详见检测工作内容附件 18。`
- 需求文档中的登录、速记、统计、我的，属于完整需求；建议按“可裁剪的二期/收尾功能”排期，不阻塞核心工作流（见第 5 节）。

以下计划默认按**单人全职开发**估算，若两人并行可适当压缩总日历时间。

## 3. 数据模型设计

### 3.1 表间关系

```text
users（本地名单，可选）
  │ 1
  ▼ N（报告人/部门快照）
defects（缺陷检测报告）────┐
                         │ N            1
projects ────────────────┘ 可空外键
  │ 1
  ▼ N
measurement_records（立柱/横梁检测记录，按 template_type 区分）
  │ 1
  ▼ N
thickness_readings（每记录 1~6 个检测面 A~F，每面 5 个厚度值）
```

关系要点：

- `projects` 1—N `measurement_records`：一个项目可有多条立柱/横梁记录，删除项目级联删除其检测记录。
- `measurement_records` 1—N `thickness_readings`：一个记录可含 1~6 个面，每面固定 5 个读数；最小值由 5 个值计算，不冗余存储。
- `projects` 1—N `defects`（可空）：缺陷报告可选绑定项目；删除缺陷仅解除关联，删除项目时缺陷保留但 `project_id` 置空。
- `defects` 冗余“报告人/部门”快照字段：即使以后调整本地用户名单，历史报告不受影响。

### 3.2 表结构建议

> 现有 `defects.db` 只有 PoC 测试数据，建议在 MVP 起步时直接按新 schema 重建；
> 正式版本上线前再补一个带 `PRAGMA user_version` 的迁移脚本，避免以后破坏真实数据。

```sql
PRAGMA foreign_keys = ON;

-- 本地用户名单（登录校验用，MVP 早期可先用代码常量，再落库）
CREATE TABLE users (
    id              INTEGER PRIMARY KEY AUTOINCREMENT,
    name            TEXT NOT NULL,
    department      TEXT NOT NULL,
    department_code TEXT NOT NULL,              -- 4 位大写字母
    employee_no     TEXT,
    created_at      TEXT NOT NULL DEFAULT (datetime('now','localtime'))
);

-- 项目
CREATE TABLE projects (
    id           INTEGER PRIMARY KEY AUTOINCREMENT,
    project_no   TEXT NOT NULL UNIQUE,          -- 项目编号
    house_name   TEXT NOT NULL,                 -- 房屋名称
    house_address TEXT,                         -- 房屋地点（选填）
    client_org   TEXT,                          -- 委托单位（选填）
    test_date    TEXT,                          -- 检测日期（选填，YYYY-MM-DD）
    created_at   TEXT NOT NULL DEFAULT (datetime('now','localtime')),
    updated_at   TEXT NOT NULL DEFAULT (datetime('now','localtime'))
);

-- 立柱/横梁检测记录（同一张表，template_type 区分；编辑时不可切换类型）
CREATE TABLE measurement_records (
    id              INTEGER PRIMARY KEY AUTOINCREMENT,
    project_id      INTEGER NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
    template_type   TEXT NOT NULL CHECK (template_type IN ('column','beam')),
    floor           TEXT NOT NULL,              -- 如“六层”
    member_position TEXT NOT NULL,              -- 如“1”/“6°”
    size_result     TEXT,                       -- 尺寸结果，如“82×76”
    requirement_text TEXT,                      -- 截面尺寸要求（保存选择时的文案快照）
    sort_order      INTEGER NOT NULL DEFAULT 0, -- 维持录入顺序
    created_at      TEXT NOT NULL DEFAULT (datetime('now','localtime')),
    updated_at      TEXT NOT NULL DEFAULT (datetime('now','localtime'))
);

CREATE INDEX idx_measure_records_project
    ON measurement_records(project_id, template_type);

-- 每个检测面的 5 个厚度值；最小值展示/导出时计算
CREATE TABLE thickness_readings (
    id         INTEGER PRIMARY KEY AUTOINCREMENT,
    record_id  INTEGER NOT NULL
               REFERENCES measurement_records(id) ON DELETE CASCADE,
    face       TEXT NOT NULL CHECK (face IN ('A','B','C','D','E','F')),
    value_1    REAL,
    value_2    REAL,
    value_3    REAL,
    value_4    REAL,
    value_5    REAL,
    UNIQUE (record_id, face)
);

-- 缺陷检测报告（在 PoC 的 defects 表上扩展）
CREATE TABLE defects (
    id                  INTEGER PRIMARY KEY AUTOINCREMENT,
    project_id          INTEGER REFERENCES projects(id) ON DELETE SET NULL,
    defect_type         TEXT NOT NULL,
    project_part        TEXT NOT NULL,          -- 工程部位
    risk_level          TEXT NOT NULL CHECK (risk_level IN ('高','中','低')),
    rectification_plan  TEXT NOT NULL,          -- 整改方案
    related_standards   TEXT,                   -- 相关规范（多行，选填）
    extra_advice        TEXT,                   -- 补充建议（选填）
    reporter_name       TEXT NOT NULL,          -- 报告人（登录用户快照）
    reporter_department TEXT NOT NULL,          -- 部门
    image_path          TEXT,                   -- 隐患图片文件路径（≤20MB）
    created_at          TEXT NOT NULL DEFAULT (datetime('now','localtime'))
);

CREATE INDEX idx_defects_project ON defects(project_id);
CREATE INDEX idx_defects_risk    ON defects(risk_level);
CREATE INDEX idx_defects_created ON defects(created_at DESC);

-- 速记（二期功能，先行占位）
CREATE TABLE notes (
    id         INTEGER PRIMARY KEY AUTOINCREMENT,
    content    TEXT,
    image_path TEXT,                            -- 每条速记 1 张
    created_at TEXT NOT NULL DEFAULT (datetime('now','localtime'))
);
```

### 3.3 设计决策说明

1. **立柱/横梁共用一张记录表**：两模板字段结构完全一致，仅模板名称与“截面尺寸要求”下拉选项不同，用 `template_type` 区分最省成本；将来若加“玻璃”模块，再扩展为第三种类型或独立表。
2. **截面尺寸要求存文案快照**：下拉选项维护在代码常量中（对齐需求文档预置条文）。保存时把所选文案写入 `requirement_text`，避免未来调整选项后旧报告内容变化。
3. **最小值不落库**：Word 导出和页面展示时对 5 个值做计算，保持单一数据来源。
4. **隐患图片存文件路径而非 base64 入 DB**：Web 版落地时图片存 `uploads/defects/` 相对路径，Word 导出时嵌入；避免 SQLite 膨胀。若后期需要严格“数据不出设备/单文件备份”，再改回 BLOB 或打包方案。
5. **统计不需要独立表**：报告总数、等级分布、7 天活动、缺陷类型 Top5 均可用 SQL 聚合现算。

## 4. 需要新增/修改的功能模块

| 模块 | 类型 | 说明 |
| --- | --- | --- |
| 数据库层 | 新增 | schema.sql + 连接/迁移工具；从 PoC 的单表升级为多张表 |
| 项目管理 | 新增 | 项目增删改查；列表显示编号/名称/记录数；删除二次确认并提示级联影响 |
| 立柱/横梁检测记录 | 新增 | 两种模板的表单：楼层、构件位置、尺寸结果、厚度检测（1~6 个面 × 5 值，实时显示最小值）、截面尺寸要求下拉；编辑时模板类型锁定 |
| 项目级 Word 导出 | 新增（核心改造） | 按样例结构输出：项目信息段 → 立柱表（有记录才输出）→ 横梁表（有记录才输出）→ 固定备注；**不输出玻璃模块** |
| 报告导出附页 | 新增 | 关联缺陷报告按“检测报告附页（N/总数）”追加，每份独立成页 |
| 缺陷检测填报 | 修改 | PoC 基础上增加：相关规范、补充建议、隐患图片、绑定项目、报告人自动带出；保留已有四字段 |
| 报告管理 | 新增 | 列表（倒序、等级徽标、缩略图、顶部统计）、按等级筛选、详情大图、删除并自动解除项目关联 |
| 登录/导航壳 | 新增（可后置） | 本地用户名单校验 + 会话保持；Web 端把“底部 4 Tab”改造成顶部/侧边导航 |
| 我的 | 新增（可后置） | 用户信息卡、数据概览、清空速记/报告（二次确认、不可恢复）、退出登录 |
| 统计 | 新增（可后置） | 报告量、等级分布、近 7 天活动、缺陷类型 Top 5 |
| 速记 | 新增（二期） | 需求中列明，但与“报告生产”主线解耦，建议放在二期 |

> “单条缺陷导出 Word”的 PoC 能力保留为内部工具或删除；对外只保留**项目级导出**，因为正式交付物是“项目编号_房屋名称_检测报告.docx”。

## 5. 开发顺序建议

排序原则：**先让用户能把“项目 + 检测记录 + 一份像样的 Word 报告”跑通**，再补缺陷报告关联与外围管理功能；速记、统计等可在 12 月中旬前按余量决定是否做。

### 阶段 M0 —— 代码底座（第 1~2 周）

- 按第 6 节拆分包结构；
- 落地 schema.sql、`db.py`、常量与预置选项；
- 用样例 docx 建立导出对照夹具（fixture）；
- **验收**：全新 clone 后 `pip install -r requirements.txt && python app.py` 即可运行，空库自动建表。

### 阶段 M1 —— 项目 + 检测记录录入（第 3~5 周）

- 项目管理页与项目详情页；
- 立柱模板录入（先做一种，横梁复用同一套代码）；
- 厚度检测 A~F 面 × 5 值输入，前端实时算最小值；
- **验收（第一个用户可用点）**：用户能新建一个真实项目，把一栋楼的立柱/横梁数据完整录入、编辑、删除。

### 阶段 M2 —— 项目级 Word 导出（第 5~8 周）

- 实现与样例一致的表头合并（厚度检测结果列跨 1~5 子列 + 最小列）、单元格居中、要求列自动换行；
- 输出“项目信息段 + 立柱表 + 横梁表 + 固定备注”，玻璃模块不出表；
- 文件名 `项目编号_房屋名称_检测报告.docx`；
- **验收**：用 M1 录入的数据导出的报告，与 `金骐智谷_金骐_检测报告.docx` 逐列比对视觉一致。

### 阶段 M3 —— 缺陷报告完善与项目关联（第 8~10 周）

- 填报页补齐图片/规范/建议/绑定项目字段与校验；
- 项目详情页展示关联报告，Word 导出支持“附加 N 份并导出 / 仅导出检测报告”二选一；
- **验收**：绑定项目的缺陷能作为附页出现在导出文档中，删除缺陷后关联自动解除。

### 阶段 M4 —— 报告管理与外围功能（第 10~13 周）

- 报告管理列表/筛选/详情/删除；
- 登录、导航壳、我的（信息卡 + 数据清理）；
- 统计（若时间允许）；
- **验收**：覆盖需求文档主流程的完整演示可用。

### 阶段 M5 —— 测试、打磨与缓冲（第 13~15 周）

- 边界用例：空项目导出、20MB 图片、路径异常、删除确认；
- 逐表与真实样例对拍；
- 清理开发期遗留（如 `check_db.py`、单条导出入口）；
- 编写简版使用说明；
- **验收**：12 月中旬可按 MVP 范围交付。

> 速记、统计属于可裁剪项。若进度吃紧，优先砍速记；其次砍统计；核心四模块（项目、检测记录、Word 导出、缺陷报告）不砍。

## 6. 代码结构调整建议

PoC 目前 `app.py` 已同时承担路由、DB、Word 生成；加入项目和导出后建议拆成 Flask Blueprint 包结构。理由：Word 导出逻辑和数据库操作需要独立测试，堆在路由文件里会迅速不可维护。

```text
D:\project\Capstone\
├── app.py                      # 入口：create_app() 后 app.run()
├── requirements.txt
├── webapp/                     # 应用包（替代根目录散放）
│   ├── __init__.py             # create_app()、蓝图注册、启动时建库
│   ├── config.py               # 路径常量、预置缺陷类型/截面要求选项
│   ├── db.py                   # get_conn()、init_db()、迁移入口
│   ├── schema.sql
│   ├── routes/
│   │   ├── __init__.py
│   │   ├── pages.py            # 首页/导航壳
│   │   ├── projects.py         # 项目 CRUD + 检测记录蓝图
│   │   ├── defects.py          # 缺陷填报 + 报告管理蓝图
│   │   └── auth.py             # 登录/退出（后置）
│   ├── services/
│   │   ├── word_report.py      # 项目级 Word 排版/附页生成
│   │   └── stats.py            # 统计聚合查询（后置）
│   ├── templates/
│   └── static/
├── reports/                    # 导出的 .docx（含样例参照文件）
├── uploads/defects/            # 隐患图片
├── defects.db                  # 开发库（gitignore）
└── tests/
    ├── test_db.py
    ├── test_word_report.py     # 与样例 docx 结构对拍
    └── fixtures/
```

拆包时的两个注意点：

- 模板路径统一改为 `webapp/templates`，蓝图渲染时无需额外配置；
- `reports/` 中的样例文件 `金骐智谷_金骐_检测报告.docx` 建议移到 `tests/fixtures/` 或单独 `docs/samples/`，避免与程序生成的报告混在一起。

## 8. 主要风险与待确认事项

1. **Word 版式对拍最耗时**：样例中有表头跨列合并、固定列宽、A4 版心、要求列自动换行等细节，建议第 5~8 周留足时间，并用脚本逐单元格比对，不要只靠肉眼。
2. **图片体积**：≤20MB 原图嵌入 Word 会让文件很大、生成慢；建议 MVP 先限制单张并生成压缩副本，同时保留原图路径。
3. **PoC 数据库升级**：现有 `defects.db` 表结构会变；正式跑数据前需确认允许重建还是走迁移。
4. **删除语义**：删除项目时“关联缺陷报告置空保留”是否满足业务习惯，建议由使用者确认一次，避免返工。
5. **玻璃模块**：样例含玻璃表，MVP 明确不做，但导出排版时注意不要因复用样例模板而误输出空玻璃章节。
6. **速记/统计是否纳入 12 月中旬交付**：建议默认不纳入；如需纳入，总估算增加约 6~10 人日并压缩测试缓冲。
