## 1. Python 引擎的移植边界

### 1.1 先立一条原则：判据是闸门，不是这份文档

`word_report.py` 有 936 行，但它**不是规格**：规格是 `report_layout.json`（所有版式数值）
加上 `tests/fixtures/generated_baseline.docx`（逐属性冻结的产物）。

所以本文不逐条枚举"边界值应该是多少"——那等于把 JSON 和基线抄一遍，抄错了反而误导。
本文只回答三件事：

1. **哪些语义必须存在**（丢了闸门会红）；
2. **哪些库已经能做**（直接映射，别自己拼 XML）；
3. **哪些库做不了**（6 处，需要后处理），以及**哪些可以整个丢掉**。

> 实操含义：M5 的实施顺序是"先搭骨架把 docx 生出来 → 立刻跑闸门 A → 按差异清单逐项补"，
> 而不是"读 936 行代码然后写 JS"。差异清单本身就是最好的移植指南。

### 1.5 已声明偏离机制：**经侦察与两轮实测后决定不引入**

### 1.7 JS 与 Python 的数值/字符串差异（容易漏的两处）

| 处 | 差异 | 处理 |
| --- | --- | --- |
| 最小值格式化 `format_mm` | Python `f"{v:.2f}"` 与 JS `toFixed(2)` 在 `.xx5` 边界上可能不同（二进制表示差异） | 读数本来就是 2 位小数输入，最小值必然是其中一个输入值 → `toFixed(2)` 精确。但要在 JS 侧加一个 `.005` 边界的测试；若出现差异，改为"四舍五入到 2 位再格式化" |
| 列表排序 | SQLite 的 `created_at DESC, id DESC` | IndexedDB 用 `index('created_at').openCursor(null, 'prev')`；索引项按 (key, primaryKey) 升序排列，`prev` 反向后**同 key 内即 primaryKey 降序** —— 正好等价 |
| `stats()` 的 `COALESCE` | SQL 的 `SUM(...)` 在空表返回 NULL，所以要 `COALESCE` | IndexedDB 的 `index.count(key)` 空表返回 `0` —— **这个坑在 JS 侧自然消失**，不必移植那个 workaround |

## 2. IndexedDB 数据模型映射

### 2.1 store 与索引

数据库 `curtain_wall`，`version = 1`。对应关系如下（右侧是 `schema.sql` 里的原始定义）：

| object store | keyPath | 索引 | 对应 SQL |
| --- | --- | --- | --- |
| `projects` | `id`（autoIncrement） | `project_no` **unique** | `projects` + `UNIQUE(project_no)` |
| `measurement_records` | `id`（autoIncrement） | `project_id`；复合 `[project_id, template_type, sort_order]` | `measurement_records` + `idx_measure_records_project` |
| `thickness_readings` | `id`（autoIncrement） | `record_id`；复合 **unique** `[record_id, face]` | `thickness_readings` + `idx_thickness_record` + `UNIQUE(record_id, face)` |
| `defects` | `id`（autoIncrement） | `project_id`；`risk_level`；`created_at` | `defects` + `idx_defects_project/risk/created` |
| `images` | `id`（落盘文件名） | — | **新增**（原来在 `uploads/` 目录里） |
| `meta` | `key` | — | **新增**：schema 版本、迁移标记、上次导出时间 |

几条设计说明：

- **`id` 用 `autoIncrement`**：IndexedDB 的 key generator 只增不减，天然满足"排序稳定"的要求，与 SQLite `AUTOINCREMENT` 语义相当。
- **`defects.created_at` 单列索引**：M4 的列表排序依赖它（`created_at DESC, id DESC`），是热路径。
- **`template_type` 不做单独索引**：它只与 `project_id` 一起用（项目详情分组），复合索引已覆盖。
- **自增主键不写进业务字段**：`id` 由 store 生成，迁移导入时保留原 SQLite 的 `id`（显式给 key 即可，IndexedDB 允许在 `autoIncrement` store 里指定 key）。

### 2.2 外键与级联：IndexedDB 什么都不会替你做

IndexedDB **没有外键、没有级联、没有约束**（unique 索引是唯一例外）。`schema.sql` 里的三种行为要手写：

| SQL 行为 | IndexedDB 实现 |
| --- | --- |
| `measurement_records.project_id REFERENCES projects ON DELETE CASCADE` | 删项目时：在一个 `readwrite` 事务里，用 `[project_id,…]` 索引游标取该项目的所有记录 → 对每条记录再用 `record_id` 索引删掉它的读数 → 最后删项目。**必须同一事务**，否则中途失败会留下孤儿读数 |
| `thickness_readings.record_id REFERENCES measurement_records ON DELETE CASCADE` | 删单条记录时同上（取读数 → 删读数 → 删记录），同一事务 |
| `defects.project_id … ON DELETE SET NULL` | 删项目时用 `index('project_id')` 游标把每条的 `project_id` 改成 `null` 再 `put` 回去。**注意这是"保留报告、解绑"，与级联删除语义相反**，Python 侧有测试锁着，JS 侧也要有 |
| `defects.project_id` 可选 | store 里允许 `project_id === null`；因为用的是**索引**而不是 JOIN，`null` 的记录不会出现在 `index('project_id')` 游标里（这正是我们要的：未绑定的报告不属于任何项目） |
| `UNIQUE(record_id, face)` | 复合唯一索引 `[record_id, face]`；插入重复会抛 `ConstraintError`，与 SQLite 的 `IntegrityError` 对应，错误处理要映射 |
| `UNIQUE(project_no)` | `projects` 的 unique 索引；新建/编辑项目时捕获 `ConstraintError` → 与现有"项目编号已存在"提示一致 |

> **一条不在 SQL 里、但必须补上的约束**：`defects` 原表的 `CHECK (risk_level IN ('高','中','低'))`。
> IndexedDB 没有 CHECK，只能在**服务层（repo）**校验，且要保证导入路径也走同一个校验函数。

### 2.3 事务：能跨 store，但有个致命陷阱

需求原文（本项目 M1 定下的语义）：**"新增检测记录时，记录 + 读数必须同一事务"**。IndexedDB 满足：

```js
const tx = db.transaction(['measurement_records', 'thickness_readings'], 'readwrite');
// 一个事务里跨两个 store 写 → 要么全成，要么全不成
```

**陷阱（本设计里最容易踩的一个）**：`IDBTransaction` 会在"没有挂起请求、微任务队列清空"时
**自动提交**。所以下面这种写法是错的：

```js
const tx = db.transaction(['…'], 'readwrite');
const id = await addRecord(tx, record);       // ← 这个 await 让出控制权
const rows = await fetchSomethingFromServer(); // ← 任何 await 非 IDB 的 Promise
await addReadings(tx, id, rows);               // ← tx 已经提交，抛 TransactionInactiveError
```

规则（写进代码注释与 review checklist）：

1. 事务内**只** `await` IDB 请求包装出来的 Promise；
2. 不要在事务里调 `fetch` / `setTimeout` / `await` 用户交互 / `structuredClone` 大对象；
3. 需要先算好数据（例如"最小值"不需要算、但"图片压缩"必须提前完成），**再开事务**；
4. 所有写操作收口到一个 `withTransaction(stores, mode, fn)` 辅助函数里，禁止业务代码自己开事务。

### 2.4 排序

| 场景 | 原 SQL | IndexedDB |
| --- | --- | --- |
| 报告列表 | `ORDER BY created_at DESC, id DESC` | `defects.index('created_at').openCursor(null, 'prev')`（见 1.7 说明） |
| 项目列表 | `ORDER BY id DESC` | `projects.openCursor(null, 'prev')` |
| 项目下的记录分组 | `WHERE project_id=? ORDER BY template_type, sort_order` | 复合索引 `[project_id, template_type, sort_order]` 上 `IDBKeyRange.bound([pid], [pid, []], false, false)` 正序游标 |
| 某记录的读数 | `WHERE record_id=?`（最多 6 条） | `index('record_id').getAll(recordId)` 后按 `face` 排序（数据量极小，不必再建索引） |

### 2.5 统计

M4 的 `stats()` 是一条 `COUNT(*) + SUM(CASE WHEN …)` + `COALESCE`，JS 侧改成：

```js
const [total, high, medium, low] = await Promise.all([
  store.count(), store.index('risk_level').count('高'),
  store.index('risk_level').count('中'), store.index('risk_level').count('低'),
]);
```

四个 `count()` 各自走索引，比一次全表游标更快；`COALESCE` 的坑不存在（见 1.7）。
**语义要点不变**：统计恒为全量，不随筛选变化（M4 有测试锁这个行为，JS 侧要保留同样的断言）。

### 2.6 版本升级与一次性数据迁移

- `onupgradeneeded` 里按 `oldVersion` 分支建 store/索引 —— 与 `schema.sql` 的"幂等建表"等价。
- **`db.py` 的旧库检测逻辑要移植**：原来 `_reject_legacy_schema` 会检测"没重建的 PoC 旧库"并给出指引；
  JS 侧对应"检测到 `meta.schemaVersion` 缺失/过旧 → 提示先导出备份再升级"。
- **SQLite → IndexedDB 的一次性导入**（不写这一步，用户现有数据就丢了）：

  1. 新增 `tools/export_sqlite_to_json.py`：读 `defects.db` + `uploads/defects/`，产出
     `backup.json`：`{projects, records, readings, defects, images: [{name, mime, base64}]}`；
  2. PWA 里加**导入页**（放在「我的 → 数据管理」）：选择 `backup.json` → 校验 → 在
     **单个事务**里写入全部 store（含 `images` 的 Blob 还原）→ 写 `meta.importedAt`；
  3. 导入是**幂等可重入**的：先清空再导入，或按 `id` 覆盖（选后者，避免"导入到一半"产生混乱）；
  4. 导入后立刻提示跑一次"自检"（闸门 C，见 4.1）。

## 3. 图片存储

### 3.1 三个方案

| 方案 | 优 | 劣 | 结论 |
| --- | --- | --- | --- |
| **IndexedDB Blob** | 全平台可用；离线；事务内与记录一起提交；备份/导出简单 | 配额受限；Safari 对非持久化源有清理策略 | ✅ **选它** |
| File System Access API | 原图落在用户可见的文件夹，几十 GB 也不挤配额；桌面体验好 | **Chromium 独占**，Safari/Firefox 没有；每次会话要用户手势重新授权 | ❌ 主方案不行。可作为"桌面增强"（导出/导入整个文件夹），二期再说 |
| 继续用 OPFS（Origin Private File System） | 大文件友好、同步 API 写入 | 仍是 Chromium 优势项；导出要给用户得再走一层 | ⚠️ 备选：若 3.5 的配额实测不够，再切 OPFS（`FileSystemWritableFileStream`） |

选 IndexedDB 的决定性理由：**目标用户是现场手机（需求 1.2"可能无网络"）**，
而 iOS Safari 不支持 File System Access API。为一个桌面才有的能力牺牲主场景不划算。

### 3.2 `images` store 的记录结构

```js
{
  id: "8f2d3be871bf479dac134a276d6c8442_缺陷照片.jpg",  // keyPath，沿用原落盘名
  blob: Blob,              // 原图（未做任何有损处理）
  thumb: Blob,             // 240px JPEG 缩略图（见 3.4）
  width: 1600, height: 1200,       // 原图（EXIF 摆正后）像素尺寸
  bytes: 2_345_678,
  mime: "image/jpeg",
  created_at: "2026-09-25 10:00:00"
}
```

**key 设计沿用 `<uuid4hex>_<清洗后的原名>.<ext>`**：这样"从 key 反推原始文件名"这条既有原则
（Python 侧 `original_name_from_path`）**原样保留**，不需要额外的 `original_name` 字段，
也不需要数据迁移去补字段。文件名清洗规则与 `sanitize_original_name` 一致。

### 3.3 压缩与 EXIF 摆正（canvas 管线）

```
File/Blob（原图）
  → createImageBitmap(blob, { imageOrientation: "from-image" })   // ① EXIF 摆正
  → OffscreenCanvas(w, h) → ctx.drawImage(bitmap)                 // ② 等比缩放到 ≤1600
  → canvas.convertToBlob({ type: "image/jpeg", quality: 0.8 })    // ③ 现压（不落库）
```

要点：

- **EXIF 摆正**：`imageOrientation: "from-image"` 由浏览器按 EXIF Orientation 自动旋转
  （Chrome 79+ / Safari 15+）。降级方案：手写解析 EXIF 的 Orientation tag（约 30 行）+ canvas
  `setTransform` 旋转。**必须验证**：手机竖拍照片在两种路径下都摆正。
- **缩略图同理**，只是目标 240px / quality 0.75。
- **canvas 重新编码会丢掉 EXIF** —— 这是好事：产物已经摆正，不会出现"再摆一次"的双重旋转。
- 透明通道（PNG）要**先铺白底**再画（对应 Python 的 `_flatten_to_rgb`），否则 JPEG 出黑底。
- 压缩是**导出时现压**（沿用"派生值不落库"），但**缩略图例外**（3.4）。

### 3.4 缩略图：对"派生值不落库"的一次**有意偏离**

Python 侧列表缩略图是"请求时现压 + `Cache-Control: immutable` + 浏览器 HTTP 缓存兜住"。
纯静态 PWA 里**没有这一层 HTTP 缓存**：列表每渲染一次就要重新解码原图（20MB 的 JPEG 解码
在手机上约 0.1~0.3s/张，20 条报告就是 2~6 秒，不可接受）。

所以：**导入时生成并保存 240px 缩略图 blob**。这是一次有意的原则偏离，理由与代价写清楚：

| | Python（现状） | M5 |
| --- | --- | --- |
| 缩略图 | 请求时现压，靠 HTTP 缓存 | 导入时生成，存 `images.thumb` |
| 违背"派生值不落库"吗 | 不违背 | **违背**（这是刻意的） |
| 为什么可以 | — | 它是**可从原图重新生成**的纯派生值（参数固定 240px/q75），不是新的业务事实；且存在同一 store 里，不存在"两种存储状态"的同步问题 |
| 代价 | — | 每张图多占 ~10~20KB；改缩略图参数需要批量重建（提供"重建缩略图"工具） |
| 全尺寸导出副本 | 现压，不落库 | **仍然现压，不落库**（每次导出只压一遍，可以接受） |

### 3.5 配额与持久化（现场工具的**真实**风险）

- 单张原图上限 20MB（`config.MAX_IMAGE_BYTES` 不变）；一次检测几十张就是几百 MB。
- 启动时调 `navigator.storage.estimate()` 显示"已用/可用"，接近上限时提示清理并阻止继续上传。
- **必须申请持久化**：`navigator.storage.persist()`。**iOS Safari 对非持久化站点有约 7 天的
  闲置清理策略** —— 对"现场记录、回办公室导出"的用法来说，这是丢数据的风险，必须在 UI 里明示
  （「我的 → 数据管理」显示是否已获持久化授权 + 一键导出备份）。
- 导出备份：把 `backup.json` + 图片打包成一个 `.zip`（JSZip 已随 `docx` 引入）下载。

### 3.6 与现有数据的一致性

`images` store 与原 `uploads/defects/` 是**同一个语义**（原图证据、不可变）。
删除报告时同事务删除图片记录（对应 M4 的"先删库后删文件"，在 IndexedDB 里变成同一事务，
比原来更安全）；"清除全部报告"同理。

## 4. 对拍基线的复用

### 4.1 三道闸门（分工不同，不互相替代）

| 闸门 | 比什么 | 期望 | 用途 |
| --- | --- | --- | --- |
| **A 移植验收** | JS 生成物 **vs** `tests/fixtures/generated_baseline.docx`（Python 引擎冻结产物），逐属性 | **0 差异** | 证明"JS 复刻了 Python"。这是 M5 的主判据 |
| **B 版式对齐** | JS 生成物 **vs** `tests/fixtures/检测表_真实裁剪.docx`（真实报告裁剪版），逐属性 | **0 差异** | 证明"仍然对齐客户报告"。理论上 A 绿则 B 绿（Python 已过 B），但 B 是**唯一**能发现"两边一起错"的闸门 |
| **C 无 Python 自检** | JS 生成物 vs `generated_baseline.fingerprint.json`，在 JS 里跑同一套指纹/差异逻辑 | **0 差异** | 给没有 Python 的环境（PWA 自身、CI 里的 Node 步骤）用；也让"用户在手机上导出后自检"成为可能 |

**为什么 A 和 B 都要**：A 只能证明"和 Python 一样"，如果 Python 本身有未发现的偏差，A 会把它
一起继承；B 直接对着客户报告，是唯一的外部真值。两者都绿，"既复刻了参考实现、又没有偏离客户模板"
才成立。

**为什么 A 是主判据而不是 B**：A 的差异清单**更细**（基线与 JS 都用同一套生成路径的产物规格，
任何属性差都会暴露），而且**性能上可行**（基线文件就在仓库里，不需要"回灌真实报告数据"那一步）。

### 4.2 让对拍工具原样继续工作

`tools/compare_report_with_sample.py` 是**纯 OOXML 读出比较**：读两个 docx、算指纹、做 diff。
它**不关心是谁生成的文件**。所以：

- **不重写、不移植**这个工具（它是 Python 的既有资产，仍在四条基线闸门里）；
- 只加一个入口：`--generate-with js --js-cli "node tools/js/generate_report.mjs"`，
  或更简单：加 `--expected-baseline` 模式，直接比"基线文件 vs 给定文件"。

于是闸门 A 的命令变成：

```powershell
node tools/js/generate_from_fixture.mjs out.docx        # JS 引擎生成
python tools/compare_report_with_sample.py --expected tests/fixtures/generated_baseline.docx --actual out.docx
```

### 4.3 关键是这两个语言中立的中间产物

**(1) `fixture_data.json` —— 让 JS 不必实现"读文档认表"**

Python 侧的 `extract_project` / `extract_groups` 能从 docx 里认出"哪些表是检测表、哪些行是数据行"。
这套逻辑**不移植**（它是测试设施，不是产品能力）。改为由 Python 导出：

```powershell
python tools/export_fixture_data.py    # → tests/fixtures/fixture_data.json
```

```jsonc
{ "project": {"project_no": "A06YG-2026-001", "house_name": "示例项目（脱敏）", …},
  "groups": [ { "template_type": "column",
                "records": [ { "record": {…}, "faces": [ {…} ] } ] } ],
  "attachments": null }
```

**JS 引擎只实现"数据 → docx"这一半**，正是我们要移植的那一半。这同时也是移植边界的技术保障：
边界之外的东西（读文档）留在 Python，边界之内（生成文档）在 JS。

**(2) `generated_baseline.fingerprint.json` —— 让闸门 C 成立**

把 `document_fingerprint()` 的结果序列化成 JSON。**有一个必须处理的陷阱**：

> `run_props()` 返回的是 **tuple 的列表**（`[(False, None, None), …]`）。JSON 里 tuple 会变成 list，
> 读回来再比就会出现 `("a","b") != ["a","b"]` 的**假差异**。所以序列化前必须把 tuple 归一成 list，
> 或者比较时统一用 JSON 往返归一化。`layout_grid` 里的 `"^"` / `"<"` 标记是纯字符串，没有这个问题。

结构（示意）：

```jsonc
{ "version": 1, "source": "generated_baseline.docx",
  "doc": { "children": [...], "tables": [...] },     // document_fingerprint 的原样
  "full_gate": { "expected_grids": [...], "compared_tables": 2 } }
```

`--bless` 的行为随之升级：**同时**重写 `.docx` 与 `.fingerprint.json`（两者必须一起变，
否则闸门 A 与 C 会互相矛盾）。

### 4.4 Python 引擎的去留

**保留，不删。** 理由：

1. 闸门 A/C 的基准由它产出；将来若**有意**改版式（客户换模板），必须先改 Python 侧、
   重新 bless、再让 JS 跟上 —— 这正是"参考实现"的用法；
2. 它是 `report_layout.json` 的**可执行文档**：数值有歧义时，跑一遍 Python 就能看到权威产物；
3. Flask 应用的**服务层与校验逻辑**（`services/*.py`）是 JS repo 的行为规格，
   348 项测试就是它的规格说明书。

处理方式：Flask 运行时降级为 `legacy/`（或在 README 里标注"参考实现，不再作为交付入口"），
**不删测试**。新增一条仓库级断言：`report_layout.json` 只有一份，`web/assets/` 下的是构建时
复制品，测试断言两者**逐字节相同**（防止"两份规格各自漂移"）。

### 4.5 迁移期怎么用这三道闸门

```
阶段 1  JS 引擎能生成文档（哪怕只有信息段）
        → 闸门 A 的差异清单就是 TODO 列表（几百条很正常，按层级收敛）
阶段 2  表格结构对齐（列宽 → 行高 → 边框 → 合并 → 段落）
        → A 的差异数按数量级下降；每降一个数量级提交一次
阶段 3  A 归零 → 跑 B（应自动归零）→ 导出 fingerprint.json → 跑 C
阶段 4  图片/附页/文件名 全部纳入 A（附页也在基线里）
阶段 5  数据层与 UI 接线，跑通"录入 → 导出 → 对拍"
```

## 5. 工程结构、构建与运行

```
web/                              纯静态 PWA（无构建工具，原生 ES modules）
├── index.html                    window.__APP__ 之外什么都不依赖
├── manifest.webmanifest
├── sw.js                         Service Worker：应用壳 + 图片 blob 不缓存（走 IDB）
├── app/
│   ├── db.js                     open/upgrade/withTransaction（唯一允许开事务的地方）
│   ├── repo/{projects,measurements,defects,images}.js   数据层（含手写级联）
│   ├── report/
│   │   ├── spec.js               import report_layout.json（唯一规格来源）
│   │   ├── engine.js             数据 → docx（移植边界之内）
│   │   ├── postprocess.js        JSZip：docGrid / 表格补丁 / styles+theme 替换（1.4 的 6 处）
│   │   └── fingerprint.js        指纹 + diff（与 Python 版同构，供闸门 C）
│   ├── images.js                 createImageBitmap + canvas 压缩 / EXIF
│   ├── ui/                       UI 阶段已定的壳（底部 Tab / 摘要行），只换数据源
│   └── import-export.js          backup.json 导入导出
├── assets/
│   ├── report_layout.json        ← 构建时从 webapp/resources/ 复制（测试断言逐字节相同）
│   ├── report_base.docx          ← 底座模板（提供 styles.xml + theme1.xml）
│   └── fixtures/                 仅测试用：fixture_data.json / *.fingerprint.json
└── vendor/                       docx、jszip（vendored，不引入打包工具链）
```

- **不引入打包器**：与仓库现有的"零构建"风格一致（`static/js/*.js` 直接裸跑）。
  `docx` 取浏览器可用的构建产物 vendored 进 `vendor/`（ESM 还是 IIFE 在实施第一步确认）。
- **运行方式**：任意静态服务器（`python -m http.server` 也行）。**不能双击 `index.html` 用
  `file://` 打开** —— IndexedDB 在 `file://` 下受限、Service Worker 不可用、模块加载受 CORS 限制。
  这一点要写进 README。
- **路由**：客户端路由用 History API；静态服务器需 fallback 到 `index.html`（或改用 hash 路由，
  代价是 URL 变丑）。建议 History + 一句"部署时配置 fallback"，并在 README 给出
  `python -m http.server` 的说明（它本身不支持 fallback → 那就**用 hash 路由**更省事）。
  → 决策点（见第 7 节问题 4）。

## 7. 已确认的决策

| # | 问题 | 决定 |
| --- | --- | --- |
| 1 | Flask 应用怎么处置 | **保留**，标注为"参考实现，不再是对外交付入口"（它是闸门基准的来源与行为规格；客户换模板时先改 Python → 重新 bless → JS 跟上） |
| 2 | 要不要引入"已声明偏离"机制 | **不引入**：**实测 11 处全部属性级可抹平，机制收益为零** —— 11 处差异无一需要在语义上偏离基线（全是 `w:val` 形式、属性顺序、可选属性缺失、`hRule` 有无这类属性级问题），全部用补丁抹平并实测到 0 差异（201 → 0）；另有 1 处由闸门口径吸收。**注意**：闸门的两个比较器严格度不同 —— `cell_fingerprint` 会归一 `vMerge` 的 `val`，`layout_grid` 不会（所以 ⑪ 必须补） |
| 3 | 缩略图落库（对"派生值不落库"的有意偏离） | **接受**：导入时存 240px 缩略图 blob（每张多 ~10~20KB，换列表秒开）；参数变更时提供批量重建（`repo/images.js::rebuildThumbnails`，已实现并有测试） |
| 4 | 客户端路由 | **hash 路由**（`#/reports/1`）—— 任何静态服务器都能跑，包括 `python -m http.server`，不需要配 fallback |
| 5 | 导出副本要不要在导入时就压好 | **不要**：原图是证据，导入只额外存缩略图；全尺寸副本**导出时现压**（`image-pipeline.js::exportCopy`），与 Python 的 `export_copy` 同构。这样"压缩参数"是纯渲染参数，改了立刻生效 |
| 6 | 闸门 A 怎么验 `Node` 里跑不了的 canvas | **换替身，不跳过**：见 4.6 —— 尺寸/方向走**产品代码**、字节用夹具的"已摆正副本"，并且替身**在需要缩放时直接报错**，不允许祝福一个我们不会交付的产物 |
| 7 | 附页的两列表宽度要不要跟检测表一起归一到 11 列规格 | **不要**：`apply_spec_widths` 现在只在"列数与检测表规格相同"时生效。附页两列表的宽度来自需求报告 4.4，拿 11 列规格去覆盖它会把整张表判错（M5-3 踩过一次，已修 + 已加注释） |

下一步：**M5-4 UI 接线**（把 UI 阶段已定的壳从 fetch 换成 repo、hash 路由、导入/导出页），
然后是 M5-5 PWA 与验收。

### 4.6 M5-3 发现的一个**闸门盲区**（比附页本身更重要）

把附页接进引擎时发现：**段落的指纹里原本完全没有图片**（`paragraph_fingerprint` 只看
`text / jc / spacing / run_props`，而图片在 `w:drawing` 里）。这意味着——

> 一张图**漏嵌、嵌错文件、尺寸算错、方向没摆正**，闸门都会照样报"全部一致"。
> 原来闸门绿只证明"文字和表格对了"，**图片从来没被验过**。

补法（都是加法，不改既有口径）：

1. 段落指纹加 `images`：取每个 `w:drawing` 的 `wp:extent`（显示尺寸，EMU）。
   **不比** `r:embed`（关系 id）——两个引擎的 id 分配方式不同，比它只会产生假差异；
2. 文档指纹加 `media`：从 `word/media/*` 读**实际像素尺寸**（按 EXIF 摆正），排序后按多重集比较。
   这一项才抓得住"显示尺寸对、但嵌的是另一张图"；
3. 新增 `tools/verify_gate_sensitivity.py`：往产物里**逐个下毒**（改图片显示尺寸 / 换成别的尺寸的图 /
   删掉 drawing / 改一个字 / 破坏 vMerge / 改行高 / 去掉加粗），
   要求每一项都被抓到、且落在**预期的那一类路径**上；同时要求"原样一对"必须 0 差异（排除假阳性）。

现在的实测输出（7 项下毒全部被抓到）：

| 毒 | 落在（闸门报出的路径） |
| --- | --- |
| `image_extent` 图片显示尺寸改小 | `body[15].images[0][0]` |
| `drop_drawing` 删掉一个 drawing | `body[15].images.length` |
| `image_media` 换成 320×200 的图 | `media` |
| `table_text` 改一个字 | `table[2].rows[0].cells[1].paragraphs[0].text` |
| `table_merge` 破坏 vMerge | `grid[0]` |
| `row_height` 行高改 500 | `table[2].rows[0].trHeight` |
| `bold_label` 去掉加粗 | `table[2].rows[0].cells[0].paragraphs[0].run_props[0]` |

**这件事的通用教训**（答辩可以讲）：**闸门绿了，先问"这个属性到底有没有被比"**。
相等有两种来源 —— "两边真的对"和"这个属性根本没进比对"。后者更危险，因为它伪装成前者。

### 4.7 附页的期望产物从哪来（Node 没有 canvas 怎么办）

闸门 A 要在 Node 里跑，而 Node 里 `createImageBitmap` / `OffscreenCanvas` 都是 `undefined`
（本机实测 Node 25）。这里**没有走"跳过图片验证"那条路**，而是把管线在"编解码"这个接缝上切开：

| 环节 | 闸门 A 里的做法 | 是真的还是替身 |
| --- | --- | --- |
| 读图片尺寸（存储宽高） | `tools/js/image-headers.mjs`（JPEG SOF / PNG IHDR） | 真（纯字节解析） |
| 读 EXIF 方向 | **`image-pipeline.js::parseJpegOrientation`** | **真（产品代码）** |
| 按方向算显示尺寸 | **`image-pipeline.js::orientedDimensions`** | **真（产品代码）** |
| 画布变换矩阵 | **`image-pipeline.js::orientationTransform`** | **真（产品代码，被真正执行）** |
| 重采样像素 | 用夹具旁边那份 `_摆正` 副本（Pillow 生成） | **替身**（不做重压缩） |

配套的两道自锁，保证替身不会祝福假产物：

- 替身要求"画布尺寸 == 可用字节的尺寸"，**对不上直接抛错**；
- 需要缩放时必然对不上（字节没缩），于是**缩放路径在闸门 A 里是硬的**——
  所以夹具图片一律 ≤1600px（`imageMaxPixels`）。缩放路径由
  `web/tests/image_pipeline.test.mjs` 的尺寸断言 + `M5-真机验证checklist.md` 的 B4/B5 覆盖；
- 闸门的 `media` 检查再独立核对一次"嵌进去的字节到底多大"。
