# v1.0.0 交付清理（branch `release/v1.0.0`）

> 目标：把课程项目的产物清理成**客户可以直接在内网部署**的最终版本，并产出一个干净的静态包。
> 分支策略：`master` 保持开发线（全部里程碑文档、测试、Flask 参考实现都在）；
> `release/v1.0.0` 只做"交付需要的改动"，不重构架构。

---

## 0. 一句话说清这次做了什么

1. 去掉**用户看得见的**开发/课程痕迹（模块进度表、开发者名字、Flask 运行说明），
   关于页改成产品信息页；
2. 把写死的「报告人 / 部门」变成**每台设备可配置**的设置项（IndexedDB `meta` 表），
   出厂默认值改为「检测员 / 检测部」；
3. 写两份客户文档（部署 + 数据/备份/FAQ），配 Nginx / IIS / 零依赖静态服务三套样例；
4. 用一个可重跑的脚本产出 `dist/mcc-inspection-tool-v1.0.0.zip`（53 个文件，465 KB），
   并在打包时做自检（必需文件、禁止项、离线清单一致性、调试输出残留）。

## 2. 两个设计决定（都不显然，写下来免得被"优化"掉）

### 2.1 产品身份放 `web/app/product.js`，而不是 `config.js`

`web/app/config.js` 是 `tools/export_web_assets.py` 从 `webapp/config.py` **生成**的
（那是 Flask 参考实现的业务配置，作为对拍基准被冻住了，不允许手改）。产品名称、版本号、
出品方属于"这一版怎么交付"，与业务规则无关，所以放在**手写**的 `product.js` 里：

- 重新生成资产不会覆盖它；
- **版本号只有一处真相源** —— `tools/make_release_zip.py` 读它来命名压缩包，
  界面用 `versionLabel()` 加 `v` 前缀，`release.test.mjs` 有一条测试禁止 HTML/manifest 写死版本；
- 客户要改的就是这一个文件（说明书第 4.2 节）。

### 2.2 个人信息放 `meta` 表，而不是新建 store

`meta` 是建库时就有的 key→value 表（本来只放 `schemaVersion`）。个人信息是单例配置，
放进去**不需要升 DB 版本**，于是老用户升级时不存在"库结构不匹配 → 打不开"的风险 ——
现场工具最不能承受的就是这个。配套的三条纪律写进了 `repo/profile.js` 的文件头：

1. 取不到就用出厂默认值（"没配过"与"配成默认"行为等价，不需要初始化步骤）；
2. 保存时去空白 + 限长（这一栏会原样写进 Word 附页）；
3. 它是**当前设备**的设置，**不进备份 zip**（备份是业务数据快照）—— 换设备要重填，
   说明书第 4.1/第 5 节都写明了。

报告里存的是**写入当时的快照**（`reporter_name` / `reporter_department`），所以改个人信息
不会回溯改历史报告 —— 这与 Python 侧 `defects` 表冗余快照字段的设计一致。

## 3. 为什么这些改动不会碰坏 Word 版式

三道闸门（A 复刻冻结基线 / B 真实报告 / C 无 Python 自检）比的都是**报告产物**。
本次只动了界面、配置与交付流程，没有动 `web/app/report/**`。结果：

- 闸门 A（两半）、B、C 全部 **0 差异**；
- `python tools/verify_all.py` **16 条全绿**；Python 348 项、前端 **226** 项。

唯一与报告内容有关的一处：缺陷填报的「报告人」从常量改成读设置项。**闸门用的夹具数据显式
给出了报告人**（`web/assets/fixture_data.json`、`tools/attachment_fixture.py`），所以两种来源
产出的附页完全一致 —— 这也是为什么改默认值不会让闸门红，而真机上署名确实变了。

## 5.1 真实浏览器端到端（E2E）—— 发布前新增的最后一道关

`python tools/verify_all.py`（Python + jsdom + 版式闸门）之后，再加一层**真实浏览器**：

```powershell
npm install            # 只需一次（@playwright/test；用本机已装的 Edge/Chrome，不下载浏览器）
npm run test:e2e       # 21 条：主流程 / 移动端布局 / 边界负载 / 离线 / 图片管线 / 鲁棒性 / 数据安全
```

它**以交付包本身为被测对象**：`web/e2e/serve-release.mjs` 把 `dist/*.zip` 解到
`_work/e2e/site/`，再用包里自带的 `serve_static.py` 起服务 —— 连部署一起验。
断言落在产物上（python-docx 打开 + Pillow 读像素），不是"按钮点了没报错"。

这一轮抓出并修掉的 3 个真问题（详见 `v1.0.0-浏览器E2E验证报告.md`）：

| # | 级别 | 问题 | 修法 |
| --- | --- | --- | --- |
| 1 | **P0** | 「导入备份」100% 失败：`zip.files.filter is not a function`（JSZip 的 `zip.files` 是对象）。客户唯一的救命通道 | 改成 `Object.entries(zip.files)`；**新增 `web/tests/import_export.test.mjs`（8 项）** + E2E 用例，并做阳性对照 |
| 2 | P1 | `web/e2e/` 会被打进交付包（62 vs 53 个文件） | 打包排除 `e2e`，并加"测试资产进包就拒绝产出"的硬断言 |
| 3 | P2 | 操作条「取消」只有 28×22px（误触就丢表单） | `styles/m5.css` 给 44×44 触控区；另加 `scroll-margin-bottom` 防软键盘遮挡 |

> **为什么 P0 能活过 234 个测试 + 16 条闸门**：备份导入当时**一条测试都没有**。
> 导出有覆盖、导入没有 —— 于是"导出能用"掩盖了"导入不能用"。这与 M5 里 `boot()` 没被测到同源：
> **没写测试的功能，等于没验过。** 现在导出与导入两侧都有 Node 测试与 E2E 闭环。

**第二轮：安卓模拟器（MuMu + MAA）交叉验证。** 同一个交付包放进安卓模拟器，用
MAA 的截图/坐标点击走系统级 UI（权限弹窗、相机、文件选择器、模态确认），再用 CDP over adb
做断言：**14 项全绿、零控制台错误**，其中关键的一项是"备份 → 清除全部报告 → 导入备份"在
真机环境里复核通过（回执、计数、缩略图重建、恢复后仍能导出）。
脚本：`npm run test:android`（= `node web/e2e/android-remote.mjs`，前置条件写在文件头）。
详见 `v1.0.0-浏览器E2E验证报告.md` 第 6.1 节。

**收尾两项（封版前最后点的）：**

| 项 | 结论 |
| --- | --- |
| 添加到主屏幕 / 独立窗口 / 离线 | ✅ 通过（Android Chrome 实测：`installabilityErrors` 为空 → 菜单「安装应用」→ 桌面图标「幕墙检测」→ 启动 `WebappActivity`，`display-mode: standalone`、无地址栏、断网 reload 正常）。**前提：https 或 localhost**（浏览器安全上下文）—— 内网 http 下业务功能正常但没有离线/独立窗口，已写进客户文档。 |
| 真软键盘遮挡保存按钮 | ❌ **发现，已修复**：键盘弹起时 `innerHeight` 不变（774）、只有 `visualViewport.height` 掉到 478，`position: fixed; bottom: 0` 的「保存/取消」被键盘整个盖住。修法：`web/app/ui/viewport.js` 把键盘高度写进 `--keyboard-inset`，`m5.css` 让 `.action-bar { bottom: var(--keyboard-inset) }`。复验：键盘 296px → 操作条抬到 `417..478`（正好压在键盘上沿），保存按钮可见可点。回归：`web/tests/keyboard_inset.test.mjs`（5 项）。 |

> 为什么用 `bottom` 而不是 `transform`：`transform` 会给固定元素建新的层叠上下文，
> 安卓 WebView 上实测会让点击命中判定错位（保存按钮明明在屏幕上，却被表单元素"挡住"）。

## 7. 下一个版本怎么做（接手的人看这段）

1. 在 `master` 上开发并跑通 `verify_all`；
2. 切 `release/vX.Y.Z`，改 `web/app/product.js` 的 `version`；
3. `python tools/export_web_assets.py`（离线缓存版本会自动变）→ `python tools/verify_all.py`；
4. `python tools/make_release_zip.py` → 得到新的 zip 与 sha256；
5. `npm run test:e2e` —— **必须以新包为准重跑**（它测的就是 `dist/` 里的 zip）；
6. 需要的话更新 `docs/release/客户部署与使用说明.md` 的版本号与 FAQ（它会被打进包里）。

> 顺序很重要：**先出包、再跑 E2E**。E2E 的被测对象是 zip，不是源码目录；
> 改了代码却没重新打包就跑去测试，验的是上一版（这个坑踩过两次，已把
> `reuseExistingServer` 改成 `false`，端口被占用会直接报错而不是悄悄测旧包）。

回滚：`release/*` 分支与 `master` 互不影响；交付出问题可以直接用上一版 zip 重新部署
（静态包是自包含的，服务器上覆盖文件即可）。
