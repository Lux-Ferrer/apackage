术语对齐：**「报告」= `defects` 表里的一行 = 一份缺陷检测报告**。它在需求里叫「报告管理」，在代码里沿用
`defects`（表名 / 服务模块名），UI 文案统一叫「报告管理」「缺陷报告」。这是需求词汇与既有代码词汇的
既定映射，M4 不为了改名而改表。

**为什么「删除即解绑」不需要额外 SQL**：需求 3.4e 说「如已绑定项目，删除后自动解除与该项目的关联」。
我们的关联就存在 `defects.project_id` 这一行上，删掉这行关联自然消失，**不需要**
`UPDATE defects SET project_id = NULL`。那句需求是针对「报告与项目是两份数据」的设计写的；我们这里
一份数据一体两面。对应到验收，就是「删除后项目详情页的关联报告列表不再出现它」。

### 1.1 为什么拆成两个蓝图而不是全塞进 `/defects`

需求报告把「缺陷检测填报（3.3）」和「报告管理（3.4）」写成**两个模块**，App 结构里也是两个入口。
路由跟着需求走，好处有三个：

1. **UI 阶段不用再改路由**。你已确定「M4 之后做 UI 改造」，届时底部导航要有「报告管理」这个 Tab；
   现在把 `/reports/` 占好，UI 阶段只搬入口、不动路由，避免二次适配（这正是当初定「UI 放最后」的理由）。
2. **只读和管理与写入分离**，`/reports/*` 全是幂等 GET + 一个 DELETE，将来要做权限/审计有干净的切面。
3. `/defects/<id>`（详情）与 `/defects/new`（填报）语义本来就不同，混在一个前缀下，
   列表该放哪儿都会别扭（放 `/defects/` 就与 POST 创建同址）。

**代价很小且已知**：`tests/test_web.py` 有 5 处引用旧路径需要跟着改（第 9 节逐行列了），
且 `/defects/<id>` 保留重定向，M3 期间的旧书签不失效。

### 1.2 列表页的筛选用「纯链接」，不用 JS

```html
<a class="stat" href="{{ url_for('reports.index') }}">全部 {{ stats.total }}</a>
<a class="stat {{ 'active' if level == '高' }}" href="{{ url_for('reports.index', level='高') }}">高 {{ stats.high }}</a>
```

顶部统计的四个数字块**同时就是筛选控件**（这是移动端最省空间的写法，也是需求 3.4b + 3.4c 的自然合并）。
纯链接意味着：无 JS、可分享 URL、浏览器前进后退可用、M5 换成客户端渲染时逻辑不变。

参数校验：`level` 只接受 `config.RISK_LEVELS` 里的值。**非法值不报错，按"不筛选"处理并在页面上给一行提示**
（`?level=紧急` 这种是用户手打或旧链接，给 400 会让人以为页面坏了）。这一条要有测试锁住。

### 1.3 删除：POST + 应用内确认弹窗

复用既有的 `base.html` 里的 `<dialog id="confirm-dialog">` 与 `app.js` 的 `data-confirm`，
与项目删除完全同一套机制（M1 已建，`app.js` 不动）：

```html
<form method="post" class="inline-form" action="{{ url_for('reports.delete', report_id=card.id) }}"
      data-confirm="确认删除报告 #{{ card.id }}（{{ card.defect_type }}）？隐患图片会一并删除，此操作不可恢复。{% if card.project_label %}该项目「{{ card.project_label }}」的关联会同时解除。{% endif %}"
      data-confirm-ok="确认删除">
    <button type="submit" class="link danger-link">删除</button>
</form>
```

删除后 `flash("报告已删除：#%d（%s）" % ...)` 并 302 回列表，保持与项目删除一致的反馈方式。

## 2. 页面设计

### 2.1 列表 `/reports/`（需求 3.4a + b + c）

顶部统计条（四个数字块，即筛选控件）：

```
┌────────┬───────┬───────┬───────┐
│ 全部 12│ 高 3  │ 中 6  │ 低 3  │      ← 统计恒为全量，不随筛选变化
└────────┴───────┴───────┴───────┘
```

下面是一列**卡片**（不是表格），每张卡：

```
┌──────┬──────────────────────────────────────┐
│      │ 密封胶开裂            [高]           │
│ 缩略 │ 东立面三层 1# 立柱                    │
│  图  │ 金骐智谷（JCZG-2026-001）             │
│      │ 2026-09-22 10:00        [详情] [删除] │
└──────┴──────────────────────────────────────┘
```

**为什么用卡片而不是 `<table class="grid">`**：项目列表没有图片，表格在手机上勉强能看；
报告列表必须带缩略图，而「左图右文 + 徽标」在手机上天然是卡片，表格要重排成卡片得写一堆
`display:block` 的 CSS 手术。现在就用卡片标记 = UI 阶段少改一遍（交接点 5.2）。

排序：`created_at DESC, id DESC`。**`id DESC` 是必需的次级排序键** —— `created_at` 精度只到秒，
案例数据与批量录入经常在同一秒内产生多条，只按时间排会导致列表顺序在不同查询间抖动。
（`services/defects.py::list_for_project` 已经是这个写法，保持一致。）

### 2.2 详情 `/reports/<id>`（需求 3.4d）

- **大图**：`<img class="photo" src=".../image">`，`max-width:100%`、`max-height:60vh`、`object-fit:contain`，
  点击开原图（`target="_blank"`）；图片缺失时渲染占位块 + 「图片文件缺失」提示
  （M3 已有 `missing` 这个概念，`test_attachment_export.py::test_attachment_renders_when_image_file_is_missing`
  证明这是真实会发生的情况）。
- 全字段：缺陷类型、工程部位、隐患等级（徽标）、整改方案、相关规范、补充建议、报告人（部门）、提交时间、
  绑定项目（可点回项目详情）。
- 操作：删除（带确认弹窗）、返回列表、去项目导出。

现模板 `defects/success.html` 的 H1 是「报告已保存」——作为管理页的详情这不合适。改法：
**H1 改为「缺陷报告 #{{ id }}」**，创建成功后由路由 `flash("报告已保存")` 给出反馈。
这样一套模板服务两个场景，不维护两份。

`badge` 的等级 → CSS 类映射（`高→high / 中→medium / 低→low`）现在写在模板里
（`success.html` 第 15 行的内联字典）。M4 用到它的地方变成三处（列表卡、详情、统计块），
**提到 `config.RISK_BADGE_CLASSES`** 做单一真相源。

## 3. 图片缩略图怎么处理

结论：**不复用 `export_copy`，新增一个 `images.thumbnail_bytes()`**；不落盘、不落库，靠浏览器缓存。

### 3.1 为什么不复用 `export_copy`

| | `export_copy`（M3，Word 用） | 缩略图（M4，列表用） |
| --- | --- | --- |
| 最长边 | 1600px | **240px** |
| 质量 | 80 | 75 |
| 输出 | 写到临时目录的**文件** | 直接返回 **bytes** |
| 生命周期 | 随导出临时目录销毁 | 随 HTTP 响应 |

1600px 的副本塞进列表，一屏 10 张就是十几 MB 流量——现场用手机流量打开列表会很难受。
两个用途的尺寸差 6.7 倍，共用一个函数只能靠参数硬凑，不如各自一个函数、共用底层。

### 3.2 具体做法

`webapp/services/images.py` 追加：

```python
def _oriented_rgb(relative_path, max_pixels):
    """打开原图 → 按 EXIF 摆正 → 超过 max_pixels 就等比缩小 → 转 RGB。

    返回 (image, was_large)；原图缺失/路径越界返回 (None, False)。
    export_copy 与 thumbnail_bytes 共用，保证两处的摆正/降采样行为一致。
    """

def thumbnail_bytes(relative_path, max_pixels=240, quality=75) -> bytes | None:
    """列表缩略图：内存现压，返回 JPEG 字节。任何失败返回 None（渲染层降级为占位块）。"""
```

路由：

```python
@bp.get("/<int:report_id>/thumbnail")
def thumbnail(report_id):
    report = _report_or_404(report_id)
    data = images.thumbnail_bytes(report["image_path"]) if report["image_path"] else None
    if data is None:
        abort(404)
    response = current_app.response_class(data, mimetype="image/jpeg")
    # 落盘文件名含 uuid，且系统没有"替换图片"的路径 → 同一个 URL 的字节永不改变
    response.headers["Cache-Control"] = "private, max-age=31536000, immutable"
    return response
```

**`immutable` 的依据**（不是随手写的）：`save_upload()` 生成的落盘名是 `<uuid4hex>_<原名>.<ext>`，
缺陷填报只有「新增」没有「改图」，所以某个 URL 对应的图片字节在生命周期内**不可能变化**。
浏览器缓存一次即可，不需要校验、不需要失效逻辑。

**不落盘缓存**：不建 `uploads/defects/.thumbs/`。理由是它要引入失效规则（虽然当前不会失效），
而浏览器缓存已经把重复解码的代价消掉了。代价是**同一张图换一个浏览器/清缓存后会重新解码一次**
（PIL 解码一张 20MB JPEG 约 0.1~0.3s）。报告量级是几十到几百，可接受；真到性能问题，
M5 的 IndexedDB blob 方案会直接把这层替掉。

**渲染层的存在性检查**：列表要显示占位块还是 `<img>`，需要在渲染前知道文件在不在。
加一个轻量 `images.exists(relative_path) -> bool`（只做 `stat`，不解码），
路由把它算进卡片视图（`card.has_image`）。这样文件缺失时显示「图片文件缺失」占位块，
而不是浏览器的碎图图标。

### 3.3 这算不算「派生值落库」原则的例外？

不算。缩略图**既不落库也不落盘**，与「最小值不落库、导出时现算」同构：它是渲染产物，
参数（`max_pixels` / `quality`）改了立刻生效，历史数据不需要回填。三个尺寸常量放进 `config`：
`THUMBNAIL_MAX_PIXELS = 240`、`THUMBNAIL_JPEG_QUALITY = 75`。

## 4. 顶部统计与筛选的 SQL

### 4.1 统计：一条 SQL，必须 `COALESCE`

```sql
SELECT COUNT(*) AS total,
       COALESCE(SUM(CASE WHEN risk_level = '高' THEN 1 ELSE 0 END), 0) AS high,
       COALESCE(SUM(CASE WHEN risk_level = '中' THEN 1 ELSE 0 END), 0) AS medium,
       COALESCE(SUM(CASE WHEN risk_level = '低' THEN 1 ELSE 0 END), 0) AS low
  FROM defects;
```

**`COALESCE` 不是装饰**：空表时 `COUNT(*)` 是 `0`，但 `SUM(...)` 对零行聚合返回 **NULL**，
页面就会显示「高 None」。空库是演示和测试的第一现场，这条要有测试锁住。

不用 `GROUP BY risk_level` 再在 Python 里折叠的理由：那需要两次查询（总数 + 分组），
两次之间理论上可以插入新数据，导致总数 ≠ 高+中+低；一条 SQL 天然自洽。

范围注意：**这里不用 `WHERE`，统计恒为全量**。需求 3.4b 的「顶部统计」和 3.4c 的「筛选」是两件事，
统计块同时兼作筛选控件只是 UI 复用，数字本身不随筛选变化（否则筛选后「高 3」变成「高 3」而「全部」变成 3，
用户会误以为数据被删了）。

### 4.2 列表：按需拼 `WHERE`，不写 `(? IS NULL OR ...)`

```python
def list_reports(risk_level=None):
    """报告列表（含绑定项目信息）。risk_level 为 None 时不筛选。"""
    sql = ["""
        SELECT d.*, p.project_no, p.house_name
          FROM defects d
          LEFT JOIN projects p ON p.id = d.project_id
    """]
    params = []
    if risk_level:
        sql.append("WHERE d.risk_level = ?")
        params.append(risk_level)
    sql.append("ORDER BY d.created_at DESC, d.id DESC")
    return db.query_all(" ".join(sql), tuple(params))
```

几个刻意选择：

- **`LEFT JOIN` 而不是 `INNER JOIN`**：缺陷报告可以不绑项目（`project_id` 可空），
  用内连接会把这些报告从列表里静默丢掉。
- **按需拼 `WHERE` 而不是 `(? IS NULL OR d.risk_level = ?)`**：后者写法短，但让 SQLite 无法用
  `idx_defects_risk`（表达式里带参数，优化器不能做索引选择）。前者是两条确定的计划。
- **`d.*` + 项目两列**，一条 SQL 出全部卡片所需字段，避免每行再查一次项目（N+1）。
  列表页渲染 N 张卡 → 1 次统计 + 1 次列表 = **恒为 2 次查询**，与行数无关。
- **分页：本期不做**。数据量级是几十~几百，需求也没要求。将来要加分页的位置就是
  `ORDER BY` 之后追加 `LIMIT ? OFFSET ?`，并把 `stats()` 的 total 用作页数——接口形状不用变。

### 4.3 删除

```python
def delete(report_id):
    """删除报告：先落库删（拿到图片路径），提交后再尽力删文件。"""
    row = get(report_id)
    if row is None:
        raise LookupError("报告不存在：#%s" % report_id)
    with db.transaction() as conn:
        cursor = conn.execute("DELETE FROM defects WHERE id = ?", (report_id,))
        if cursor.rowcount == 0:
            raise LookupError("报告不存在：#%s" % report_id)
    images.remove(row["image_path"])      # 提交之后才动文件；失败不影响数据一致性
    return row
```

**顺序是有理由的，不是随手排的**：先删库、后删文件。反过来的话，文件删了而 DELETE 失败
（约束冲突/磁盘错误），就会留下一条指向不存在图片的记录——**用户可见的数据损坏**。
按这个顺序最坏情况只是留下一个孤儿文件（不可见、不影响任何功能），可接受；
真要做清理，M5 的边界用例阶段加一个「孤儿文件扫描」脚本即可。

`images.remove()` 本身就吞掉 `ValueError/OSError`（M3 写的），所以「图片已经被手工删掉」
这种情况不会让删除失败——这一条也要有测试。

## 6. M4 完成后，UI 改造的接手点

你已确认的顺序是 **M4 → UI（静态壳 + 客户端渲染）→ M5（IndexedDB + docx JS，去掉 Flask）**。
所以 M4 的真正交付物不只是页面，还有**一个 UI 阶段不需要再改数据层的接口形状**。五条具体交接点：

### 6.1 模板里不写业务逻辑（最重要）

所有派生/展示用字段由路由预先算好，模板只做 `{{ }}` 输出：

```python
# routes/reports.py
def _card(row) -> dict:
    """一条报告的展示视图。模板与将来的 JS 渲染器都只消费这个形状。"""
    return {
        "id": row["id"],
        "defect_type": row["defect_type"],
        "risk_level": row["risk_level"],
        "badge_class": config.RISK_BADGE_CLASSES[row["risk_level"]],
        "project_part": row["project_part"],
        "created_at_text": defect_service.format_report_time(row["created_at"]),
        "project_label": ("%s（%s）" % (row["house_name"], row["project_no"])
                          if row["project_id"] else ""),
        "has_image": images.exists(row["image_path"]),
        "thumbnail_url": url_for("reports.thumbnail", report_id=row["id"]),
        "detail_url": url_for("reports.detail", report_id=row["id"]),
    }
```

于是 `list.html` 里没有 `sum(...)`、没有 `'高' if ... else`、没有时间格式化、
没有 URL 拼接。**UI 阶段把这个 dict 用 `jsonify` 发出去、用 JS 渲染成同样的卡片，
就是一次机械搬运**，不需要重新理解业务。`_card()` 本身可以直接单测（不进请求上下文也能测
`badge_class` / `project_label` 这些分支）。

### 6.2 卡片拆成独立 partial

`templates/reports/_card.html` = 一张报告卡的全部标记，`list.html` 只负责循环。
UI 阶段的 JS 渲染器有 1:1 的参照物，改样式只改这个文件。

### 6.3 缩略图保持「URL 返回字节」，不内联 base64

现在返回 `image/jpeg` 字节 + `Cache-Control: immutable`，将来静态壳换成 IndexedDB 的
`URL.createObjectURL(blob)` 时，只改 `<img src>` 的来源，图片处理逻辑（`thumbnail_bytes`）
可以直接移植成 JS 或保留在本地服务里。

### 6.4 筛选用服务端渲染的纯链接

没有 JS 状态、没有 `fetch`、没有客户端路由。UI 阶段要在前端筛选时，
`stats()` 与 `list_reports(level)` 已经是「传参就返回数据」的纯函数，
前端筛选只要把同一份全量数据在客户端过滤即可，不需要重写查询。

### 6.5 入口已经全在路由表里

M4 把「报告管理」挂进 `base.html` 导航和首页 `MODULES`，
UI 阶段只需把这几个入口搬到底部 Tab/侧边导航，**不再涉及新增路由**。

> 一句话总结接手点：**M4 结束时，`/reports/` 的每一个 URL、每一份数据形状都已经定稿；
> UI 阶段改的是"怎么画"，不改"去哪儿取数"。**
