## 1. 为什么必须再做这一层

`docs/management/M5-设计.md` §9 已经记过一次：四个真机 bug 里有三个是"jsdom 比浏览器宽容"造成的。
这次又验证了三处新差异，都不是理论推演：

| 能力 | jsdom / Node | 真浏览器 | 这次抓到的事 |
| --- | --- | --- | --- |
| canvas / `createImageBitmap` | 无（只能用替身） | 有 | EXIF 方向、透明 PNG 铺白底、等比缩放，第一次被真正执行 |
| `<dialog>.showModal()` | 未实现（代码走 `confirm()` 降级） | 有 | 模态确认路径第一次被真正执行（备份清除/导入都靠它） |
| Service Worker / Cache | 无 | 有 | 离线刷新、缓存完整性、断网导出，第一次被真正执行 |
| `URL.createObjectURL` + `<a download>` | 桩（拦下来记一笔） | 真下载 | 真实文件名、真实 zip/docx 字节（用 python-docx / Pillow 复验） |
| 视口 / 布局 | 常量 | 可缩放 | 软键盘压到 400px、横屏 812×375、桌面 1280×900 |
| `Blob`/`File`/IndexedDB 结构化克隆 | 混合（要 Node 的 File） | 一致 | `zip.files` 类型错误这类"只有真路径才走得到"的 bug |

**一句话**：这些测试不是在重复跑单元测试，而是在跑"用户真正走的那条路"。

## 4. 发现并修复的 3 个真问题

### 4.1 【P0 · 数据安全】「导入备份」100% 失败：`zip.files.filter is not a function`

- **怎么发现**：第 20 条用例（备份 → 清除 → 导入）在真实浏览器里点「导入备份」，
  确认弹窗**永远不出现**；点完只看到提示条 `导入失败：zip.files.filter is not a function`。
- **根因**：`web/app/import-export.js::inspectBackup()` 写了
  `zip.files.filter(...)`，而 JSZip 的 `zip.files` 是**对象**（`{路径: ZipObject}`）不是数组。
  界面在导入前**必须先调它**（先给用户看清"将覆盖什么"再确认），所以这条唯一的救命通道
  必然失败 —— 客户现场出问题想恢复数据时，会 100% 撞上。
- **为什么之前没被发现**：**备份导入当时一条测试都没有**。
  234 个 Node 测试里没有 `import_export.test.mjs`，E2E 之前也不存在；
  而 `exportBackup()`（导出）是有 E2E/UI 覆盖的 —— 于是"导出能用"掩盖了"导入不能用"。
  这与 M5 里 `boot()` 没被测到是同一类漏洞：**没写测试的功能，等于没验过**。
- **修法**：
  ```js
  const listed = new Set(
      Object.entries(zip.files)
          .filter(([name, entry]) => name.startsWith(IMAGE_PREFIX) && !entry.dir)
          .map(([name]) => name.slice(IMAGE_PREFIX.length)),
  );
  ```
- **补的测试**：
  - `web/tests/import_export.test.mjs`（**新增 8 项**）：往返导入、覆盖语义、图片随包走 +
    缩略图重建、缺图/孤儿图对账、坏图降级、四种坏备份拦截、失败不落半截状态。
  - E2E 第 20 条：真实 `<dialog>` 确认 + 真实 `File` + JSZip 解析 + 恢复后重新导出。
- **阳性对照**：把修法改回去，新增测试立刻红，报的正是 `TypeError: zip.files.filter is not a function`。

### 4.2 【P1 · 交付包泄漏】浏览器测试会被打进交付包

- **怎么发现**：打包脚本提示 "暂存完成：**62** 个文件"（之前是 52）。多出来的 10 个正是
  `web/e2e/` 下的测试脚本（`.spec.mjs` + 两个 Python 辅助脚本）。
- **影响**：客户拿到的包里会多出一堆测试代码（还有断言文案、夹具生成脚本）。
  功能不影响，但这是"交付版"的体面问题，也让包内清单对不上。
- **修法**：`tools/make_release_zip.py` 的排除列表加入 `e2e`，并在 `verify()` 里加了**硬断言**：
  任何路径命中 `tests/` `e2e/` 或后缀为 `.spec.mjs` / `.test.mjs` 就拒绝产出。
- **现状**：53 个文件，`python -c "zipfile.namelist()"` 里没有任何测试资产。

### 4.3 【P2 · 移动可用性】操作条里的「取消」只有 28×22px

- **怎么发现**：第 8 条用例（触控尺寸）量出来 `取消` 是 28×22 —— 手机上很难点准，
  而它紧挨着「保存」，误触就是丢掉正在填写的整张表单。
- **修法**：`web/styles/m5.css` 给 `.action-bar > a` 一个 44×44 的最小触控区
  （视觉上仍是文字链接）。顺带加了 `scroll-margin-bottom`：手机聚焦输入框时，
  浏览器只保证"滚进视口"，并不知道底部还压着一条固定操作条。
- **复验**：第 3、8、14 条用例通过；在 375×812 与压到 400px 高（模拟软键盘）两种情况下，
  聚焦的输入框都完整露在操作条之上。

> 另外修掉两个**测试自身**的坑（记录在此，避免下次重踩）：
> ① 本地残留的静态服务器让 Playwright `reuseExistingServer: true` 安静地测了**旧的解包副本**
> （改了 CSS 却验的是旧包）—— 现已改为 `false`，端口被占用就直接报错；
> ② `locator.click()` 在 Playwright 里默认**没有超时**，找不到元素会一直等 →
> 表现为"下载事件超时"这种误导性错误。用例里已保证先导航到有该按钮的页面。

## 6. 只有真浏览器能验的六件事（这次全部首次通过）

1. **EXIF 方向**：存储 1200×800 + `Orientation=6` 的 JPEG → 页面显示 800×1200、
   缩略图 800×1200、**写进 docx 的像素也是 800×1200 且红带在顶部**（色带位置可判定"没摆正/摆两次"）。
   这是 `createImageBitmap({imageOrientation:'from-image'})` 真实行为的第一次验证。
2. **透明 PNG 铺白底**：RGBA 图的透明区导出后是**纯白**（`corner=[255,255,255]`），不是黑块。
3. **大图等比压缩**：2400×1800 → 1600×1200，且**只有这一张**在附页里标「已压缩」。
4. **Service Worker 离线**：缓存 44 个文件齐全、版本号与 `VERSION.txt` 一致、
   断网刷新可用、**断网还能导出 Word**（docx 生成全在本地）。
5. **模态确认弹窗**：`<dialog>.showModal()` 的真实路径（jsdom 里走的是 `confirm()` 降级分支），
   清除与导入两个破坏性操作都验证了"弹窗出现 → 显示影响面 → 确认后执行"。
6. **真实下载**：文件名（含中文、含非法字符清理）、字节内容、python-docx 可打开。

### 6.1.3 收尾两件事：PWA 安装/离线 与 真软键盘

这两项是"封版前最后要点的"，都在模拟器里做完了，而且**各抓到一个真问题/硬约束**。

**(1) 添加到主屏幕 → 独立窗口 → 断网可用：通过，但有个前提**

| 步骤 | 结果 |
| --- | --- |
| 以 `http://10.0.2.2:8124`（普通 http）打开 | 业务功能全部正常，但 `navigator.serviceWorker` **不存在** —— 不是安全上下文，SW 根本不会注册 |
| 换成 `http://localhost:9000`（`adb reverse` 把宿主端口映射到设备 localhost） | `isSecureContext: true`；SW **registered / activated / controller=true** |
| Chrome 自己的可安装性判定 `Page.getInstallabilityErrors` | **`[]`（空 = 可安装）** |
| 菜单 →「安装应用」→ 确认 | 弹窗显示**应用图标 + 名称「建筑幕墙检测报告工具」+ 站点地址**；确认后桌面出现图标「幕墙检测」（manifest 的 `short_name`） |
| 从桌面图标启动 | 启动的是 `WebappActivity`，`matchMedia('(display-mode: standalone)') === true`、`browser` 分支为 false，`innerHeight 830 / screen 854` → **没有地址栏的全屏独立窗口** |
| 断网后 reload | 应用照常渲染（`route: projects.index`、标题与 Tab 都在）——SW 从缓存供壳 |

> **硬约束（写进了客户文档）**：离线与"装成独立应用"需要**安全上下文**（`https://` 或 `localhost`）。
> 内网 `http://192.168.x.x:8080` 部署时：**业务功能全部正常，但没有离线、只能加普通快捷方式**。
> 这是浏览器的规矩，不是实现缺陷；需要离线就配内网 HTTPS。

**(2) 真软键盘：发现「保存」被键盘挡住 → 已修复并复验**

- **现象**：模拟器自带输入法（搜狗）在 Android 15 上渲染不出来、还会吞掉底部触摸（`mInputShown=true`
  但没有键盘窗口，`Window #5 InputMethod` 压在浏览器之上）→ 换装了 **Simple Keyboard** 才拿到真实键盘。
- **实测**：键盘弹起时 `innerHeight` **不变**（774），只有 `visualViewport.height` 从 774 掉到 **478** ——
  于是 `position: fixed; bottom: 0` 的「保存 / 取消」被键盘**整个盖住**（修复前 `bar.bottom = 774 > 478`）。
- **修法**：`web/app/ui/viewport.js` 监听 `visualViewport` 的 resize/scroll，把"键盘占掉的高度"写成
  `--keyboard-inset`；`styles/m5.css` 里让 `.action-bar { bottom: var(--keyboard-inset, 0px) }`。
  （**不用 `transform`**：会给固定元素建新的层叠上下文，安卓 WebView 上实测让点击命中判定错位。）
- **复验**（真实键盘）：键盘 296 px → `--keyboard-inset: 296px` → 操作条从 `713..774` 抬到 **`417..478`**
  （正好压在键盘上沿）、「保存」按钮 `426..470` 可见可点、聚焦输入框 `198..242` 仍可见、`body.keyboard-open` 生效。
- **回归**：`web/tests/keyboard_inset.test.mjs`（5 项：纯函数、CSS 变量、阈值、无 visualViewport 时空操作）

### 6.1.4 这一轮发现的三件事（都不是产品缺陷，但都值得记）

1. **模拟器镜像里没有浏览器**：MuMu 这个镜像只装了游戏与 WebView 提供者，没有可启动的浏览器。
   我装了 **Bromite 108（Chromium / x86）** 作为测试用浏览器 —— 也就是说"安卓端验证"的第一步
   其实是"先给它一个浏览器"。
2. **换浏览器之前踩到一个浏览器的坑**：先用的是一个老的 WebView 壳浏览器（Lightning）。
   它把页面排版成 **830 CSS px 高**（`innerHeight` / `visualViewport` / `documentElement.clientHeight`
   三者一致），但屏幕上只露出约 **775** px —— 于是 `position: fixed; bottom: 0` 的底部 Tab
   被推到屏幕外，看起来像"应用的 Tab 不见了"。用页面内探针（`elementFromPoint` +
   `getComputedStyle`）确认**应用自身的布局是对的**（`display:flex`、top 774、命中测试正常），
   换成 Chromium 内核浏览器后一切正常。
   **教训**：真机验证发现"UI 不见了"时，先量一遍 `elementFromPoint` —— 可能是浏览器的
   视口计算有问题，而不是你的 CSS。
3. **这个 WebView 没有暴露 Storage API**：数据管理页正确降级成「当前浏览器不提供容量信息」，
   并保留"请定期导出备份"的提醒 —— M5 设计 §3.5 的降级路径在真机上第一次被真实触发
   （Playwright 的桌面 Chrome 有 API，走的是另一条分支）。

还有一个**方法论**提醒：坐标点击的 y 必须按**当前滚动位置**算，并且要把 WebView 顶部偏移
标定出来（我用底部 Tab 的位置反推：`tabbar.top` × dpr + 偏移 = 屏幕 y）。我一开始用旧截图的
坐标去点「清除全部报告」，点了两次都没弹窗，一度怀疑是模态框的 bug；标定后一次点中，
并监听了 `close`/`cancel` 事件确认**弹窗稳定停留、没有任何异常关闭**。

## 8. 残留风险（已知限制）

| 风险 | 现状 | 建议 |
| --- | --- | --- |
| **iOS Safari**（EXIF 行为、`<dialog>`、IndexedDB 配额实现差异） | 本机没有 WebKit/Safari/Mac，**未验证** | 交付 iOS 用户前，用一台真 iPhone（iOS 16.4+）按原 checklist B/D 组走一遍 |
| **触控手势**（长按、双指缩放、惯性滚动） | 只验证了单指点击与滑动 | 现场如遇手势类问题，按截图复现再补 |
| 内网 `http://` 下**没有离线、装不成独立应用** | 浏览器安全上下文的硬约束（SW 只在 https / localhost 注册） | 需要离线就配内网 HTTPS；已写进客户文档 |
| 换 origin（协议 / 域名 / 端口）会看到"空库" | IndexedDB 按 origin 隔离 | 部署地址一次定好；变更前先导出备份，再到新地址导入 |
| 少数老浏览器 / 自带壳浏览器的视口 bug | 实测会把 `position:fixed;bottom:0` 推出屏幕（应用自身布局正确，探针可证） | 建议用 Chrome / Edge / Safari；"按钮不见了"先查浏览器 |
| 厂商输入法异常（模拟器上的搜狗） | 与产品无关（换标准输入法后正常） | 现场遇到输入异常先换输入法 |

> 两轮下来的分工很清楚：**Playwright（桌面 Chrome）负责"功能与产物正确"**，
> **模拟器 + MAA/CDP 负责"安卓环境与系统交互"**（相机、文件选择器、模态弹窗、PWA 安装、真键盘）。
> 唯一没被这两层覆盖的是 **iOS**，它需要一台真 iPhone。

## 9. 一句话教训（可引用）

> **"测试环境比真实环境宽容"这件事，会一直持续到你把真实环境也测一遍。**
> 这轮新增的证据：jsdom 没有 canvas（EXIF 方向永远测不出）、
> 没有 `<dialog>.showModal`（模态路径永远走降级分支），
> 而"导出能用"的覆盖会让人以为"备份能用"—— 备份导入却一直是坏的；
> 换到安卓模拟器，又踩到"浏览器自己的视口算错，把 bottom-fixed 的 Tab 推出屏幕"。
> 补法是可执行的：**把交付包本身当被测对象，在每一层真实环境里跑一遍完整链路。**
