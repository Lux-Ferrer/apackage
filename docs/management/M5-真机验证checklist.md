# M5 真机验证 checklist（纯前端 / 离线 / 图片管线）

> 与 `真机验证checklist.md` 的分工：那份验的是 **Flask 版 UI 改造**（`python app.py --lan`）。
> 这份验的是 **M5 的纯前端版**（静态页 + IndexedDB + docx JS）——风险点完全不同：
> 那边怕"按钮点不动"，这边怕**丢数据**（配额/持久化）、**照片方向不对**、**离线打不开**。
>
> **执行时机**：M5-4 已把 UI 接到数据层，**现在就能跑**（用 `python tools/serve_web.py`）。
> 记录格式与那份一致：`编号 | 通过/失败 | 机型 / 系统 / 浏览器 | 现象 + 截图`。

## 0. 先看这一节：哪些必须你手动做，哪些我已经自动化验过了

| 项 | 谁来做 | 说明 |
| --- | --- | --- |
| 页面的 JS 代码本身（路由 / 录入 / 导出 / 备份） | ✅ **已自动化** | `web/tests/ui.test.mjs`：在 jsdom 里加载**真实 `index.html`** 走完「建项目 → 加记录 → 加报告（含图）→ 导出 → 下载 → 备份」15 项 |
| 模块路径 / import map（"白屏"类事故） | ✅ **已自动化** | `web/tests/module_graph.test.mjs` 5 项；另用 `python -m http.server` 实测过 10 个 URL 的 200 + MIME |
| 静态服务器能否正确服务 ES modules | ✅ **已自动化** | `.js` → `text/javascript`、`.docx` → 正确的 MIME（实测输出记录在 M5 设计 §5） |
| 导出产物的版式（含附页图片） | ✅ **已自动化** | 闸门 A（两半）+ 闸门 B 都是 **0 差异**；闸门敏感性 7 项下毒全被抓住 |
| **浏览器的 `createImageBitmap` 真实行为（EXIF 摆正）** | ⚠️ **只能你手动** | Node/jsdom 里没有 canvas，**没有任何自动化能替代这一条**。见 B 组 |
| **IndexedDB 在真实浏览器里的配额与持久化** | ⚠️ **只能你手动** | 见 A 组（`navigator.storage` 的真实数值只有真机有） |
| 真机上的触控/字号/布局观感 | ⚠️ **只能你手动** | 见 C 组 |
| 离线与"添加到主屏幕" | ⚠️ **只能你手动**（清单/SW 本身已自动化，见 D 组） | M5-5 已交付：Service Worker + manifest + 生成的离线清单。自动化只能验"清单不缺文件、版本化正确"，**真正的离线行为只有真机能验** |

**结论**：现在只剩两件必须你亲自做的事 —— **B 组（照片方向）** 和 **D 组（安装与离线）**。
B 组是唯一能验证浏览器 `createImageBitmap({imageOrientation:'from-image'})` 真实行为的途径；
D 组是唯一能验证 Service Worker 真的把应用壳缓存下来的途径。A/C 组顺带一起跑。

### 需要准备的 4 样东西

1. 一台手机（iOS 或 Android 都行，**iOS 的久坐清理策略更凶，最好用 iPhone 验 A 组**）；
2. 手机相册里一张**竖拍照片**（相机 App 拍的都有 EXIF 方向；截图/下载的图通常没有）；
3. 一张**横拍**照片、一张**大图**（>1600px，最好 >3MB）；
4. 电脑上能打开 `.docx` 的工具（Word / WPS / Pages）—— B2 要在电脑上看导出结果。

### 起服务

```powershell
python tools/serve_web.py            # 会打印"本机"与"手机"两个地址
```

手机浏览器输入打印出来的**手机地址**（形如 `http://192.168.x.x:8080`）。

> ⚠️ 用相机 App 直接拍**需要 https 或 localhost**（浏览器的安全上下文限制），
> 局域网 http 下只能用「从相册选择」。这是浏览器的规矩，不是本工具的缺陷。
> 想验"拍照"入口就先把照片存进相册。

## B. 隐患照片的方向与清晰度（**M5-3 的核心验收，先做这一组**）

**前置**：项目 Tab → 新建项目（编号 `PHOTO-01`、名称 `照片方向`）→
进项目详情 → 「+ 添加检测记录」→ 选「幕墙立柱」→ 随便填一条记录并保存
（楼层 `六层`、构件位置 `1`、检测面 `B`、5 个读数随便填数字）→ 保存。
（导出需要项目里有检测记录，否则会提示"还没有检测记录"。）

| # | 你要做的操作 | 怎么算通过 | 失败时记什么 |
| --- | --- | --- | --- |
| **B1** | 报告 Tab →「+ 新建报告」→ **隐患图片**选相册里那张**竖拍**照片 → 再填：缺陷类型「密封胶开裂」、工程部位「东立面三层 1# 立柱」、整改方案随便写、**绑定项目选 `PHOTO-01`** → 底部「提交保存」 | 跳到报告详情页；**大图是正的**（不是躺倒 90°、也不是上下颠倒） | 截图（原图 + 页面大图各一张）+ 机型/浏览器版本 |
| **B2** | 报告 Tab 看那条报告的**缩略图** | 缩略图**也是正的**，且不变形（宽高比与原图一致） | 截图 |
| **B3** | 项目 Tab → 进 `PHOTO-01` 详情 → 点「**附加 1 份并导出**」→ 等提示「已导出 …docx」→ 把文件传到电脑打开 → 翻到**附页**那一页 | 附页里的照片：**方向正确**、**没有被拉伸变形**、信息表最后一行的「图片文件」写的是原文件名 | 把 docx 发我 + 说明哪一页有问题 |
| **B4** | 再新建一份报告，图片换成**横拍**照片，同样绑定项目 → 导出（此时按钮变成「附加 2 份并导出」） | 两份附页的照片都方向正确、不变形；页码是「检测报告附页（1/2）」「（2/2）」且**各自独占一页** | 截图 |
| **B5** | 再建一份报告，图片换成**大图**（>1600px） | 附页信息表「图片文件」那一行显示 **`原名（已压缩）`**（带"已压缩"） | 截图（附页那一行） |
| **B6** | 再建一份报告，图片换成**小图**（<1600px，比如截图） | 「图片文件」那一行显示 **`原名`**（**不带**"已压缩"——没缩过就不该这么说） | 截图 |

**为什么 B1 过了还要做 B3**：B1 过只说明"浏览器在渲染时摆正了"；
B3 才说明"**摆正后的像素真的被写进了 docx**"。两者是不同的代码路径 ——
B1 走 `<img>` 显示，B3 走 `image-pipeline.js` 的
`createImageBitmap` → 画布变换 → 嵌入。只有 B3 同时验证了后一半。

**失败时的判断依据**（把这条截图发我，我能直接定位）：
- 页面正、docx 躺倒 → `createImageBitmap({imageOrientation:'from-image'})` 走了降级路径
  而 `orientationTransform` 的矩阵没生效；
- 页面就躺倒 → 浏览器既不支持 `imageOrientation` 也没按 EXIF 摆正（很老的浏览器）；
- 变形（宽高比不对）→ `fitImageTwips` 或画布目标尺寸算错。

## 打不开怎么办（A/B 组之前先过这一关）

| 步骤 | 操作 | 结论 |
| --- | --- | --- |
| 1 | 电脑浏览器打开 `http://127.0.0.1:8080` | 打不开 → 服务没起来，看 `tools/serve_web.py` 的终端输出 |
| 2 | 电脑用**局域网 IP**（不是 127.0.0.1）打开 `http://192.168.x.x:8080` | 打不开 → 服务绑错了（`serve_web.py` 默认绑 `0.0.0.0`，不该出现） |
| 3 | 电脑能开、手机不能 | 查：手机是否开着 VPN（关掉）→ 是否同一 Wi-Fi（比对 IP 前三段）→ 电脑防火墙是否放行该端口 |
| 4 | 公司网/访客网 | 极可能是路由器开了**客户端隔离**（AP Isolation）。用手机开热点、电脑连手机热点再试 |
| 5 | 都不行 | 换端口：`python tools/serve_web.py --port 9000` |
| 6 | 页面一片空白 | 打开浏览器控制台看报错。**先把 Console 的红色报错截图发我** —— 白屏通常意味着某个模块路径或 import map 出了问题（自动化里有一条专门查这个的测试，所以你如果遇到，说明是浏览器兼容性问题） |
